# Bảng đặc tả Use Case — Hệ thống quan trắc chất lượng nước

Các bảng dưới đây viết theo văn phong và bố cục của mẫu bạn gửi, đồng thời bám theo các UC trong sơ đồ dự án. Mỗi bảng mô tả một UC tổng quát cùng các UC con được include bên trong.

**Từ ngữ và cách hiểu:** “site” là điểm quan trắc; “thiết bị” là ESP32/cảm biến đã đăng ký; “phép đo” là một gói dữ liệu cảm biến. Flutter gọi API để trao đổi với backend. Các mã 400, 401, 403, 404, 409 lần lượt là yêu cầu không hợp lệ, chưa xác thực, không đủ quyền, không tìm thấy dữ liệu, và dữ liệu bị gửi trùng. Các sơ đồ không có chức năng tài chính như trong ảnh mẫu.

## 1. Administration — Quản trị hệ thống

| Trường | Nội dung đặc tả |
|---|---|
| Tác nhân | Admin (quản trị viên). |
| Mục tiêu | Cho phép Admin xem và quản lý tài khoản người dùng, gồm trạng thái hoạt động và vai trò, để kiểm soát quyền truy cập hệ thống. |
| Mô tả | Admin có thể xem danh sách tài khoản, bật hoặc vô hiệu hóa tài khoản, và thay đổi vai trò giữa `USER` và `ADMIN`. Đây là UC tổng quát gồm ba UC con: **View User Accounts**, **Update Account Status** và **Change User Role**. Màn hình quản trị và API hiện có không cung cấp chức năng xóa tài khoản. |
| Ca sử dụng | Administration (Quản trị hệ thống). |
| Tiền điều kiện | Admin đã đăng nhập bằng tài khoản đang hoạt động (`ACTIVE`) và có role `ADMIN`. Các API quản trị được bảo vệ bởi Spring Security; đăng nhập của ứng dụng hiện dùng HTTP Basic, không dùng JWT. |
| Luồng sự kiện chính | 1. Admin chọn chức năng “Quản trị tài khoản” trên ứng dụng.<br>2. Hệ thống hiển thị danh sách tài khoản. Flutter gửi `GET /api/admin/users`; backend trả các tài khoản theo thứ tự mới tạo trước.<br>3. Admin chọn một thao tác trên tài khoản:<br><br>• **Xem danh sách tài khoản (View User Accounts):** Hệ thống hiển thị tên, email, vai trò, trạng thái và thời điểm tạo của từng tài khoản.<br><br>• **Cập nhật trạng thái (Update Account Status):** Admin chọn `ACTIVE` để cho phép tài khoản truy cập hoặc `DISABLED` để tạm khóa. Ứng dụng gửi `PATCH /api/admin/users/{id}/status`. Hệ thống lưu trạng thái mới và tải lại danh sách.<br><br>• **Đổi vai trò (Change User Role):** Admin chọn `USER` hoặc `ADMIN`. Ứng dụng gửi `PATCH /api/admin/users/{id}/role`. Hệ thống lưu vai trò mới và tải lại danh sách.<br><br>4. Với thao tác cập nhật thành công, backend trả thông tin tài khoản mới; giao diện hiển thị trạng thái hoặc vai trò vừa thay đổi. |
| Luồng sự kiện rẽ nhánh | • **Chưa đăng nhập hoặc tài khoản đã bị vô hiệu hóa:** Hệ thống từ chối request với mã 401; ứng dụng yêu cầu đăng nhập lại.<br><br>• **Người đăng nhập không có role `ADMIN`:** Hệ thống từ chối truy cập với mã 403.<br><br>• **Không tìm thấy tài khoản cần cập nhật:** Hệ thống trả mã 404; dữ liệu không thay đổi.<br><br>• **Admin tự khóa tài khoản hoặc tự đổi vai trò:** Hệ thống từ chối thao tác với mã 400.<br><br>• **Thao tác làm mất Admin hoạt động cuối cùng:** Không cho phép vô hiệu hóa hoặc hạ role của Admin hoạt động cuối cùng; hệ thống trả mã 400 để luôn còn ít nhất một Admin hoạt động.<br><br>• **Dữ liệu trạng thái/vai trò không hợp lệ:** Backend không lưu thay đổi và trả lỗi yêu cầu không hợp lệ.<br><br>• **Lỗi mạng hoặc máy chủ:** Ứng dụng thông báo lỗi; Admin có thể tải lại danh sách để kiểm tra trạng thái hiện tại. |
| Hậu điều kiện | • Khi xem danh sách: dữ liệu tài khoản không thay đổi.<br>• Khi cập nhật thành công: trạng thái hoặc vai trò mới được lưu trong database và được dùng để kiểm tra quyền ở các request tiếp theo.<br>• Khi thao tác thất bại hoặc bị từ chối: dữ liệu tài khoản giữ nguyên. |

## 2. Site Management — Quản lý điểm quan trắc

| Trường | Nội dung đặc tả |
|---|---|
| Tác nhân | User (người dùng đã đăng nhập). |
| Mục tiêu | Cho phép User tạo điểm quan trắc và xem các điểm do mình sở hữu để tổ chức, theo dõi dữ liệu từ thiết bị. |
| Mô tả | User có thể tạo site với tên, vị trí, múi giờ và ghi chú, sau đó xem danh sách site của mình. Múi giờ site được dùng để xác định phạm vi ngày của báo cáo. UC gồm **Create Monitoring Site** và **View Monitoring Sites**. Backend hiện có API tạo và liệt kê site; chưa có API sửa hoặc xóa site. |
| Ca sử dụng | Site Management (Quản lý điểm quan trắc). |
| Tiền điều kiện | User đã đăng nhập bằng tài khoản đang hoạt động. Mỗi thao tác đọc/ghi được giới hạn trong các site thuộc tài khoản hiện tại. |
| Luồng sự kiện chính | 1. User chọn mục “Điểm quan trắc”. Hệ thống hiển thị các site hiện có của User.<br>2. User có thể chọn một trong các thao tác sau:<br><br>• **Xem danh sách điểm quan trắc (View Monitoring Sites):** Ứng dụng gọi `GET /api/sites`. Backend chỉ truy xuất site có owner là User đang đăng nhập, sắp xếp site mới trước rồi trả danh sách để ứng dụng hiển thị.<br><br>• **Tạo điểm quan trắc (Create Monitoring Site):** User chọn “Tạo điểm quan trắc”, nhập tên và múi giờ; có thể nhập thêm vị trí và ghi chú. Ứng dụng gửi `POST /api/sites`. Backend kiểm tra dữ liệu, xác thực múi giờ, gắn site với User hiện tại rồi lưu site. Sau khi nhận kết quả thành công, ứng dụng mở/tải lại dashboard tại site vừa tạo.<br><br>3. User chọn site cần theo dõi từ danh sách. |
| Luồng sự kiện rẽ nhánh | • **User chưa có site:** Backend trả danh sách rỗng. Ứng dụng hiển thị trạng thái chưa có điểm quan trắc và cho phép bắt đầu tạo site.<br><br>• **Thiếu tên hoặc múi giờ, hoặc nội dung vượt giới hạn:** Backend từ chối lưu và trả lỗi dữ liệu không hợp lệ. Các trường bắt buộc là tên và múi giờ.<br><br>• **Múi giờ không tồn tại/không đúng định dạng:** Backend trả mã 400; site không được tạo.<br><br>• **User gửi ID site không thuộc mình khi truy cập chức năng liên quan:** Backend không trả dữ liệu của người khác và báo không tìm thấy site (404).<br><br>• **Phiên đăng nhập hết hạn hoặc lỗi kết nối:** Ứng dụng thông báo lỗi; dữ liệu chưa lưu được giữ nguyên. |
| Hậu điều kiện | • Khi tạo thành công: site mới được lưu và liên kết với User hiện tại; múi giờ hợp lệ được lưu cùng site.<br>• Khi xem danh sách: dữ liệu không thay đổi và chỉ các site của User được hiển thị.<br>• Khi tạo thất bại: không phát sinh site mới. |

## 3. Device Management — Quản lý thiết bị

| Trường | Nội dung đặc tả |
|---|---|
| Tác nhân | User. Thiết bị IoT là tác nhân gửi số đo trong UC Measurement Ingestion. |
| Mục tiêu | Cho phép User đăng ký thiết bị vào một site và theo dõi danh sách thiết bị cùng thời điểm nhận dữ liệu gần nhất. |
| Mô tả | UC gồm **Register IoT Device** và **View Devices / Last Seen**. Khi đăng ký, hệ thống sinh device code và device token để thiết bị xác thực khi gửi số đo. Khi xem danh sách, hệ thống trả trạng thái, `lastSeenAt` và cờ online được tính theo thời gian nhận gần nhất. |
| Ca sử dụng | Device Management (Quản lý thiết bị). |
| Tiền điều kiện | User đã đăng nhập và đã có site. Site được chọn phải thuộc User. |
| Luồng sự kiện chính | 1. User mở mục “Thiết bị” và chọn site cần quản lý.<br>2. Hệ thống hiển thị danh sách thiết bị của site. Ứng dụng gọi `GET /api/sites/{siteId}/devices`; backend xác minh quyền sở hữu site rồi trả thiết bị, trạng thái và `lastSeenAt`.<br>3. User chọn một trong các thao tác sau:<br><br>• **Xem thiết bị / lần gửi gần nhất (View Devices / Last Seen):** Hệ thống hiển thị từng thiết bị cùng thời điểm backend nhận số đo gần nhất. Thiết bị được xem là online khi đang `ACTIVE`, đã gửi ít nhất một phép đo và lần nhận đó nằm trong timeout (mặc định 300 giây).<br><br>• **Đăng ký thiết bị IoT (Register IoT Device):** User chọn “Thêm thiết bị” và nhập tên. Ứng dụng gửi `POST /api/sites/{siteId}/devices`. Backend xác minh site, sinh device code và token ngẫu nhiên, chỉ lưu token dưới dạng BCrypt hash, rồi trả mã và token rõ cho ứng dụng.<br><br>4. Ứng dụng hiển thị token trong hộp thoại cấu hình để User chép/cấu hình vào thiết bị. Token rõ chỉ được trả khi tạo thiết bị; cần lưu lại ở thời điểm này.<br>5. Sau khi đóng hộp thoại, ứng dụng tải lại danh sách thiết bị. |
| Luồng sự kiện rẽ nhánh | • **Chưa có thiết bị:** Backend trả danh sách rỗng; ứng dụng hiển thị trạng thái danh sách trống.<br><br>• **Thiết bị chưa gửi số đo lần nào:** `lastSeenAt` chưa có và `online=false`.<br><br>• **Thiết bị đã gửi nhưng quá timeout:** Hệ thống hiển thị thiết bị offline. Trạng thái này được tính lúc lấy danh sách, không phải do một tiến trình nền cập nhật liên tục.<br><br>• **Site không tồn tại hoặc không thuộc User:** Backend trả 404 và không tạo/trả thiết bị của site đó.<br><br>• **Tên thiết bị thiếu hoặc không hợp lệ:** Backend từ chối tạo thiết bị.<br><br>• **User không lưu token khi hộp thoại hiển thị:** Database vẫn chỉ có token hash; hiện không có API đọc lại token rõ. Cần đăng ký token mới nếu không còn token dùng cho thiết bị.<br><br>• **Lỗi mạng/server:** Ứng dụng hiển thị lỗi; User có thể thử tải lại danh sách. |
| Hậu điều kiện | • Khi đăng ký thành công: thiết bị `ACTIVE` được gắn với site; database lưu token hash; ứng dụng hiển thị device code và token để cấu hình.<br>• Khi xem danh sách: dữ liệu không đổi; User chỉ thấy thiết bị trong site của mình.<br>• Khi đăng ký thất bại: không có thiết bị mới được tạo. |

## 4. Water Quality Summary — Theo dõi chất lượng nước

| Trường | Nội dung đặc tả |
|---|---|
| Tác nhân | User. |
| Mục tiêu | Cho phép User theo dõi số đo mới nhất, xem lịch sử, xem thống kê theo ngày và mức sàng lọc của site đã chọn. |
| Mô tả | UC tổng quát gồm bốn UC con: **View Latest Measurement**, **View Measurement History**, **View Daily Water Quality Summary** và **View Screening Assessment**. Khi tải dashboard, Flutter lấy danh sách site trước, sau đó tải thiết bị, số đo mới nhất, báo cáo ngày và lịch sử. Hai chức năng tổng hợp ngày và xem đánh giá sàng lọc hiện dùng chung API `/daily-summary`; response có cả số liệu thống kê và `screeningLevel`. |
| Ca sử dụng | Water Quality Summary (Theo dõi chất lượng nước). |
| Tiền điều kiện | User đã đăng nhập và chọn site thuộc mình. Để có nội dung số đo/báo cáo, site cần có thiết bị đã gửi phép đo. |
| Luồng sự kiện chính | 1. User mở dashboard hoặc mục lịch sử và chọn site cần theo dõi.<br>2. Hệ thống hiển thị các chức năng sau:<br><br>• **Xem số đo mới nhất (View Latest Measurement):** Ứng dụng gọi `GET /api/sites/{siteId}/measurements/latest`. Backend xác minh site thuộc User, tìm phép đo có `measuredAt` mới nhất trong các thiết bị của site và trả readings, thời điểm đo, trạng thái dữ liệu và mức đánh giá. Ứng dụng hiển thị các chỉ số cảm biến gần nhất.<br><br>• **Xem lịch sử số đo (View Measurement History):** User chọn khoảng thời gian để xem. Ứng dụng gọi `GET /api/sites/{siteId}/measurements?from=...&to=...&limit=...`. Backend xác minh quyền truy cập, lấy phép đo trong khoảng từ thời điểm `from` (bao gồm) tới `to` (không bao gồm), sắp xếp mới trước và trả tối đa số mẫu được yêu cầu. Flutter dùng kết quả để hiển thị danh sách/biểu đồ. Giới hạn là 1 đến 1000 mẫu; Flutter hiện mặc định 500.<br><br>• **Xem tổng hợp chất lượng nước theo ngày (View Daily Water Quality Summary):** User chọn ngày. Ứng dụng gọi `GET /api/sites/{siteId}/daily-summary?date=YYYY-MM-DD`. Backend dùng timezone của site để xác định đầu và cuối ngày, tính số mẫu và min/trung bình/max cho nhiệt độ, pH, oxy hòa tan, độ đục và TDS, sau đó lưu mới hoặc cập nhật bản tổng hợp ngày.<br><br>• **Xem đánh giá sàng lọc (View Screening Assessment):** Flutter đọc trường `screeningLevel` trong cùng response tổng hợp ngày và hiển thị mức đánh giá cùng số mẫu. Hệ thống chỉ đưa ra mức khi đủ số mẫu tối thiểu cấu hình (mặc định 24); nếu thiếu, hiển thị `INSUFFICIENT_DATA` (“Chưa đủ dữ liệu”).<br><br>3. User có thể đổi site, ngày, khoảng thời gian hoặc chỉ số biểu đồ; ứng dụng gửi lại request tương ứng và cập nhật màn hình. |
| Luồng sự kiện rẽ nhánh | • **Site chưa có phép đo:** API số đo mới nhất trả rỗng; giao diện báo chưa nhận được dữ liệu. Lịch sử trả danh sách rỗng.<br><br>• **Ngày không có mẫu hoặc ít hơn 24 mẫu:** Báo cáo vẫn có thể hiển thị số mẫu/thống kê đang có; `screeningLevel` là `INSUFFICIENT_DATA`.<br><br>• **Khoảng thời gian sai hoặc limit ngoài 1..1000:** Backend từ chối request với mã 400.<br><br>• **Site không thuộc User hoặc không tồn tại:** Backend từ chối truy cập và trả 404.<br><br>• **Ngày sai định dạng:** Backend từ chối request; không tạo báo cáo cho ngày sai.<br><br>• **Request không được xác thực hoặc lỗi kết nối:** Ứng dụng hiển thị thông báo lỗi; không hiển thị dữ liệu mới như thể đã tải thành công. |
| Hậu điều kiện | • Các chức năng xem mới nhất/lịch sử không làm thay đổi phép đo.<br>• Khi yêu cầu báo cáo ngày, backend tính summary từ dữ liệu đã lưu và insert/update bản tổng hợp ngày trong database.<br>• `screeningLevel` là kết quả sàng lọc theo ngưỡng cấu hình của dự án, không phải kết quả kiểm nghiệm hoặc chứng nhận chất lượng nước. |

## 5. Measurement Ingestion — Tiếp nhận số đo

| Trường | Nội dung đặc tả |
|---|---|
| Tác nhân | ESP32 / Water Sensor là tác nhân khởi tạo gửi số đo. User là người theo dõi dữ liệu sau khi hệ thống tiếp nhận. |
| Mục tiêu | Nhận gói dữ liệu cảm biến, xác thực thiết bị, kiểm tra tính hợp lệ, đánh giá readings theo ngưỡng và lưu phép đo để ứng dụng theo dõi. |
| Mô tả | UC tổng quát được thiết bị thực hiện bằng HTTP API **Submit Measurement via HTTP API**. Luồng này bao gồm ba UC: **Authenticate Device Code and Token**, **Validate and Store Reading**, **Assess Reading Against Thresholds**. Endpoint ingest không yêu cầu HTTP Basic của User; thiết bị phải gửi device code trên URL và token trong header `X-Device-Token`. |
| Ca sử dụng | Measurement Ingestion (Tiếp nhận số đo). |
| Tiền điều kiện | Thiết bị đã được User đăng ký, đang ở trạng thái `ACTIVE`, có device code và token hợp lệ. Backend và database đang hoạt động. Payload có `messageId`, `measuredAt` và đối tượng readings. |
| Luồng sự kiện chính | 1. ESP32/cảm biến gửi `POST /api/device-ingest/{deviceCode}/measurements`, kèm header `X-Device-Token` và payload gồm mã gói, thời gian đo, các chỉ số cảm biến.<br>2. **Xác thực thiết bị (Authenticate Device Code and Token):** Backend tìm thiết bị có device code tương ứng và trạng thái `ACTIVE`. Hệ thống so sánh token trong header với BCrypt hash đã lưu. ## Ghi chú về phạm vi triển khai

- Tài khoản mới được đăng ký với role `USER`; việc tạo Admin ban đầu được thực hiện theo cấu hình quản trị của dự án.
- Mức sàng lọc sử dụng ngưỡng cấu hình tham khảo: pH, oxy hòa tan, độ đục và TDS. Các ngưỡng này không được trình bày như tiêu chuẩn pháp lý hoặc kết quả xét nghiệm.
- Dự án hiện không có chức năng sửa/xóa site, sửa/xóa thiết bị, xóa tài khoản, chụp ảnh hóa đơn, hoặc endpoint riêng để đánh giá sàng lọc. Những chức năng này không được mô tả như đã triển khai.
